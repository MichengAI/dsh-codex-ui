## 三、🔴 P1 严重问题（必须优先修复）

### P1-1｜安全：依赖安装接口无跨站请求防护（CSRF）

**定位**：`src/index.ts:53-58`（POST 分支）；`src/dependency-manager.ts:165-177`

```ts
if (request.method === 'POST') {
  const dependencies = await installDependency(url.searchParams.get('dependency'))
  ...
}
```

**原因分析**：该 POST 会触发真实副作用——`installDependency` 会向 npm registry 发起网络请求、`spawn` 子进程执行 `dsh plugin add`、并**改写用户 profile 目录下的 `pnpm-workspace.yaml`**。端点完全没有校验 `Origin`/`Sec-Fetch-Site`/CSRF token。浏览器任意恶意网页只需一个表单即可跨站触发：

```html
<form method="POST" action="http://localhost:3080/api/michengai/codex-ui/dependencies?dependency=ui">
```

**影响**：虽依赖名经过 `managedDependency` 白名单校验（这点做得好，不能注入任意命令），但攻击者仍可强制触发"更新插件/写用户配置文件/反复拉起子进程"，属于未授权状态变更 + 本地文件写入 + 资源滥用。

**最小修复**（`src/index.ts` POST 分支前加校验）：

```ts
const origin = request.headers?.origin ?? request.headers?.['sec-fetch-site']
// 仅接受同源请求；无 Origin 的非浏览器客户端（curl 等）仍可访问，如需更严可改为要求自定义头
if (origin !== undefined && origin !== 'same-origin') {
  const urlOrigin = new URL(request.url ?? '/', 'http://localhost').origin
  if (String(origin) !== urlOrigin) {
    response.writeHead(403); response.end(JSON.stringify({ error: '拒绝跨站请求。' })); return
  }
}
```

（注：`HttpRequest` 类型目前只声明了 `method?`/`url?`，需补充 `headers?: Record<string, string | string[]>` 字段。）

### P1-2｜正确性：置顶工作区可能在初始化竞态中被整体清空并持久化（数据丢失）

**定位**：`src/client/CodexWorkspaceBrowser.tsx:164-170`

```ts
useEffect(() => { savePinnedWorkspaceIds(storage(), pinnedWorkspaceIds) }, [pinnedWorkspaceIds])   // 164 行：持久化
useEffect(() => {                                                                                 // 167 行：清理无效 id
  const valid = new Set(workspaces.items.map(workspace => String(workspace.workspaceId)))
  setPinnedWorkspaceIds(ids => ids.filter(id => valid.has(id)))
}, [workspaces.items])
```

**原因分析**：挂载时两个 effect 都会执行。若宿主快照 store 的 `workspaces.items` 是**异步填充**的（首帧为空数组），则 167 行的清理 effect 会把全部置顶 id 过滤为空，紧接着 164 行的持久化 effect 把 `[]` 写回 localStorage——**用户的置顶列表被永久抹掉**，之后 items 加载完成也无法恢复。这是典型的"用未就绪数据覆盖持久状态"竞态。

**最小修复**（items 未就绪时跳过清理，或等首次非空再清理）：

```ts
useEffect(() => {
  if (workspaces.items.length === 0) return        // items 未加载完成前绝不清理
  const valid = new Set(workspaces.items.map(workspace => String(workspace.workspaceId)))
  setPinnedWorkspaceIds(ids => ids.filter(id => valid.has(id)))
}, [workspaces.items])
```

`pinnedSessionIds` 的持久化（165 行）同理可考虑统一收敛，但当前无清理逻辑，风险低。

### P1-3｜性能：会话观察器对全文档每次 DOM 变更做全量扫描 + 布局读取，流式输出会明显卡顿

**定位**：`src/client/conversation-header.ts:133-148`（`observeConversationHeader`）+ `src/client/conversation-bubbles.ts:37-68`

```ts
const observer = new MutationObserver(sync)
observer.observe(doc.documentElement, { childList: true, subtree: true })   // 146-147 行：观察整个文档
```

```ts
// conversation-bubbles.ts:38-44 —— sync() 每次都会执行
const rows = root.querySelectorAll<HTMLElement>('[data-chat-flow-kind="user"] ...')
const text = (bubble.innerText ?? bubble.textContent ?? '').replace(...)   // innerText 触发强制回流
```

**原因分析**：观察目标是 `document.documentElement` 的整个子树，而 DSH 会话在 agent 流式输出时**每个 token 都会产生多次 DOM 变更**。每次回调都会执行 `placeConversationTabs` / `syncTabSlider` / `decorateConversationTitle` / `decorateUserBubbles` 四次全文档 `querySelectorAll`，其中 `decorateUserBubbles` 还对每个用户气泡读取 `innerText`（强制同步布局）。会话越长、流式越快，卡顿越明显——这是本插件核心使用场景的持续性能税。

**最小修复**（rAF 节流 + 缩小观察范围）：

```ts
let pending = false
const sync = (): void => {
  if (pending) return
  pending = true
  requestAnimationFrame(() => {
    pending = false
    placeConversationTabs(doc)
    const tabs = findConversationTablist(doc)
    if (tabs !== undefined) watchTabSelection(tabs)
    syncTabSlider(doc)
    decorateConversationTitle(doc)
    decorateUserBubbles(doc)
  })
}
```

更好的方案：仅观察 `header` 元素（页签/标题改动）与 `[data-conversation-scroll]`（气泡改动），两者各挂一个轻量观察器，并把 `innerText` 换成 `textContent`。

## 四、🟡 P2 一般问题

### 正确性 / 异步竞态

**P2-1｜频道轮询无并发控制，慢响应会覆盖新数据**
`src/client/ChannelBrowser.tsx:55-67` + `src/client/channel-api.ts:67-74`
4 秒 `setInterval` 轮询，前一次 fetch 未完成时再次发起；若旧请求晚于新请求返回，`setGroups(next)` 会用**过期数据覆盖最新数据**，且无请求超时（挂死的请求永远不 resolve）。建议：`AbortController` 取消上一轮、或序列号令牌丢弃过期响应、或 `load` 加"进行中则跳过本轮"。

**P2-2｜定时会话识别边界过宽，普通会话可能被误隐藏**
`src/client/schedule-sessions.ts:17-19`
`AUTOMATION_TITLE_RE = /^\d{4}-\d{2}-\d{2} \d{2}:\d{2}/` 会把标题以"2026-08-18 20:00"开头的**用户手动重命名的普通会话**也判为定时任务，从任务树消失且出现在定时页签。建议在 `isScheduleSession` 中改为"id 前缀命中 **或** 标题命中且 `origin` 可识别为自动化来源"。

### 安全

**P2-3｜host 错误信息原样回传，可能泄露本地绝对路径**
`src/index.ts:62`：`message = error instanceof Error ? error.message : ...`。`dependency-manager.ts` 里 `readFile` 的 ENOENT 等错误会带上 profile 目录绝对路径直接返回给浏览器。本地应用风险低，但建议统一映射为固定文案，路径仅记入服务端日志。

### React 最佳实践 / 性能

**P2-4｜权限汉化观察器：每次 DOM 变更全文档扫描所有按钮 + 遍历全部文本节点**
`src/client/permission-i18n.ts:145-155`（`observe(document.body, { childList, subtree, characterData })`）
用户在输入框每敲一个字符都会触发一次全文档 `querySelectorAll('button')` + `visibleText`（读 textContent）+ `replaceEmbeddedFullAccess` 的 TreeWalker 全文替换。多数时候文档里根本没有权限菜单，属纯浪费；且 `replaceEmbeddedFullAccess` 会改写 **React 管理的文本节点**（React 重渲染后观察器再次改写，形成收敛但无谓的往返）。建议：改用 rAF 节流 + 先按 `[data-dcu-perm]` / 权限容器选择器做第一层快速过滤。

**P2-5｜侧栏宽度观察器：直写宿主 DOM 并全文档扫描 div**
`src/client/sidebar-width.ts:39-50, 52-68`
`findSidebarFrame` 在每次文档变更时遍历**所有 div** 匹配 `grid-template-columns` 正则；`applySlimSidebar` 直接改写宿主 `frame.style` 与拖动手柄 `style.left`——若宿主用 React 状态驱动这些样式，会出现"宿主重渲染复位 → 观察器再改"的拉锯闪烁。建议：缓存 frame 引用、rAF 节流、限定观察 `[data-sidebar-collapsed]` 祖先链。

**P2-6｜CodexWorkspaceBrowser 悬停提示导致整树重渲染**
`src/client/CodexWorkspaceBrowser.tsx:139-151, 283-289`
每次鼠标移入会话行都 `setHoverTip` 新对象 → 整棵工作区树重渲染；`useEffect(..., [hoverTip])` 还随 hoverTip 变化反复增删 window 监听。建议把 hover 状态限定在行组件内部（或 memo 行组件），并让监听 effect 只依赖"是否显示"。

### 可维护性

**P2-7｜三个浏览器组件重复一套菜单/重命名/删除/悬停状态机**
`CodexWorkspaceBrowser.tsx` / `ScheduleBrowser.tsx` / `ChannelBrowser.tsx`：`renameTarget/deleteTarget/renameDraft/busy/error/hideTipTimer/showTip/hideTip/dismissTip/run` 及两个 Modal 的 JSX 高度雷同（各约 80-100 行）。建议抽 `useSessionRowActions()` hook + `<SessionModals />` 组件，可净减 200+ 行并消除三处行为漂移（例如 ScheduleBrowser 的删除 Modal 缺少 `deletePending` 状态、ChannelBrowser 重命名 Modal 的 Enter 处理与另两者不一致——已是事实上的漂移）。

### 工程化与依赖

**P2-11｜pnpm-workspace.yaml 存在占位符配置**
`pnpm-workspace.yaml:4-5`：

```yaml
allowBuilds:
  esbuild: set this to true or false
```

`allowBuilds.esbuild` 的值是交互式提示文本而非布尔值，属于生成时留下的占位，应改为 `esbuild: true`（或删除该项）。当前仓库内 `pnpm install` 是否报错取决于 pnpm 对该非法值的容忍度，但这是明显的配置隐患。

**P2-12｜依赖状态查询无缓存，每次打开"关于"页并发 7 个 npm registry 请求**
`src/dependency-manager.ts:111-121`：`Promise.all` 对 7 个受管包各发一次 `fetch(registry/latest)`（5s 超时）。建议加 TTL 缓存（如 5 分钟）或仅在显式刷新时查询。

**P2-13｜依赖安装无并发互斥**
`src/dependency-manager.ts:165-177`：连续点击两个不同依赖的安装会并发 `spawn` 两个 `dsh plugin add` 子进程，pnpm 锁文件竞争可能触发 EPERM/EBUSY（错误文案会误导用户以为文件被占用）。建议进程级 `installing` 互斥锁。

### 测试质量

**P2-14｜断言测试大量依赖源码正则匹配，极其脆弱**
`tests/settings-integration.assert.ts:97` 等：断言的是**精确 JSX 源码文本**（如 `onContextMenu=\{(event) => { event\.preventDefault\(\); ...`），任何格式化/换行/变量改名都会误报失败；同时它们只验证"源码里存在某字符串"，不验证任何行为。建议：纯函数继续用行为断言（现有这部分做得不错），源码级断言收敛到少数几条关键不变量（如 `assert.doesNotMatch(client, /as never/)` 这类禁令性检查）。

**P2-15｜`tests/client-bundle.assert.ts` 依赖手工构建的 dist，`npm test` 不先 build**
该测试读取 `dist/client.js`，而 `package.json` 的 `test` 脚本不执行 `build`。若 dist 过期，测试对**旧产物**断言通过，产生假绿。建议：test 前执行 `tsdown`（仅 client 入口），或在 CI 脚本里明确 `build && test` 顺序。

**P2-16｜核心交互无行为测试**
拖拽排序、悬停定时器、键盘导航、localStorage 持久化往返、host 两个端点、`installDependency` 安装流程、`observeSlimSidebar` 的幂等性均无测试；唯一集成测试 `client-runtime.integration.spec.ts` 仅 2 例且只断言插槽条目数。建议优先补：localStorage 读写往返 + 置顶清理竞态（P1-2 的回归测试）、channel 轮询乱序、纯 DOM 适配函数（`placeConversationTabs`/`decorateUserBubbles` 的 jsdom 用例）。

### 国际化

**P2-17｜英文词典残留中文**
`src/client/locales.ts:156`：`'sidebar.imSettings': 'IM助理'` —— 英文界面下 "IM 助理" 设置入口显示为中文。`zh`/`en` 键集合由 `Record<keyof typeof zh, string>` 编译期对齐（做得好），但**值**的中英混杂没有检查。建议补充"en 词典值不含 CJK 字符"的断言测试。

## 六、正面亮点（值得保持）

1. **安全基线良好**：所有外部输入（channel 分组、依赖状态、连接器）都经过逐字段类型守卫（`parseChannelSession`/`isDependencyStatus`/`isConnector`）；所有用户数据均以 React 文本或 `textContent` 渲染，**无一处**把外部输入写入 `innerHTML`（3 处 `innerHTML` 全部是编译期常量 SVG）；依赖安装走白名单 `managedDependency` + 版本格式校验，杜绝命令注入。
2. **宿主边界 fail-fast**：`host-services.ts` 的 `requireService` 在启动即校验宿主服务能力，API 变更立即显式失败而非静默 503，是插件对宿主耦合的正确姿势。
3. **副作用清理完整**：所有 `MutationObserver`、window 监听、定时器、`AbortController`、订阅均有成对清理；`useSyncExternalStore` 的 `getSnapshot` 缓存设计（`companion-slots.ts`）正确。
4. **组件抽取合理**：`SessionRow`/`GroupHead`/`sessionMenuItems`/`SessionHoverCard` 被任务/频道/定时三棵树复用，是这次重构中最好的部分。
5. **纯函数测试扎实**：`permission-i18n`/`schedule-sessions`/`workspace-browser`/`hover-tip`/`dependency-manager` 的行为断言覆盖了主要边界，`applyReleaseExclude` 的正则编辑有针对性用例。

## 七、总体评价

这是一个**工程质量明显高于平均水平的个人/小团队插件**：类型严格模式全开、副作用纪律好、白名单式安全设计、纯逻辑与 UI 分层清晰、测试对纯函数覆盖认真。主要问题集中在三处：

1. **对宿主导入的信任假设过强**（P1-2 置顶清空竞态）——把"宿主快照必然同步就绪"当成了事实；

3. **测试的"契约"价值正在衰减**——大量源码正则断言 + 断言死代码存在（`pendingPinRef`），测试开始反过来**固化坏味道**而不是守护行为。
